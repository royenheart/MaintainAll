# Decision: Continue the source Session as a replay target

Status: implemented — a creation-time `continue-session` task delivers its triggers into the saved source Session instead of creating a seeded Run session

## Problem

The seeded replay model freezes a task at save time. For a recurring monitor that keeps analyzing new issues/PRs in the same long-lived session, that has three costs: later source-session turns are invisible to the run, the monitor has to rediscover its scope from scratch, and a resumed multi-day session can exceed the 16 MiB seed cap even though the runbook needs no trajectory at all. The user asked for a mode that directly continues the original session so the next run sees the latest context.

## Decision

- A task may bind `manifest.bindings.continueSession: { sessionId }` at creation. It is creation-time and machine-local: edits preserve it, the natural-language edit prompt says to preserve it, and export drops all bindings while import never recreates it on another machine.
- Continuation requires `taskMode: fresh` (no replay seed) and rejects `agentPreset` / `permissionPreset` bindings. Manifest validation enforces the exact binding shape and both cross-field rules centrally, so a hand-edited conflicting asset fails to load. The source Session keeps its own agent preset, permissions, title, working directory, and history; dispatch never mutates them.
- The Save dialog gains a creation-time continuation checkbox. Checking it forces the `fresh` mode and shows a hint; the control is read-only when editing. The `ops_save_task` tool gains `replayMode: "new-session" | "continue-session"`, the injected Save prompt explains it, and `POST /save` rejects a continuation save that is not `fresh` or that tries to set preset bindings.
- Seeded dispatch is unchanged. Continuation dispatch resolves the source Agent in [`src/host/replay-runtime.ts`](../../../../../../src/host/replay-runtime.ts): live Agent first, otherwise a **compatibility bridge** over the embedding's reminder activation path. In a Web composition that bridge calls dsh's `schedule/resolve-agent` waterfall (a Schedule-domain reminder extension point; documented listener is the SDK server, fallback is the Web Session controller) with `sessionController.resolveAgent` as the plugin fallback; an SDK composition may register its own handler. The bridge is not a general session-activation API: the [proposed neutral upstream extension](../../../proposed/architecture/2026-11-03-dsh-session-activation-extension.md) tracks the replacement, and the bridge is removed first when dsh provides one. A deployment with no activation provider fails closed. Activation providers own the resumed Agent's lifecycle, so a plugin unload cannot cancel the user's source Agent. An archived source Session fails closed before delivery, and a subagent-owned Session is refused in both the live and activated paths.
- No run cwd, seed rewrite, title rename, or permission-preset application happens. The trigger context plus the task asset directory and `AGENTS.md` path are injected with `followup`, so a busy source Session queues the run in dsh's inbox instead of interrupting the active turn. Activation providers keep any resumed Agent live; the plugin retains no source-Agent handle, and a bookkeeping failure after publication leaves the delivered message in place.
- The run-map records the source session id and source cwd with a generated run id, and the registry's `lastRunAt` is refreshed, so the Ops panel still shows the run and its session link. A registry re-read failure before publish returns a classified dispatch failure, and any handle supplied by a resolver is disposed on a pre-publication failure.

## Alternatives considered

- **Fork the source Session at fire time into a fresh Run session.** It would preserve isolation while carrying the latest context, but every trigger would reload and copy the whole history (possibly hitting the seed cap again), and it is not the "original session continues" behavior the user asked for. Rejected for this feature; it remains a possible later mode.
- **Make continuation a `taskMode` value.** `taskMode` describes seed capture for a new Run session; continuation is an orthogonal replay target. Adding a fourth mode would also force client/import/edit semantics for a value that stores no seed. Rejected.
- **Reuse the source Session by appending a synthetic task asset to its cwd.** Rejected: the source workspace must not be rewritten, and the runbook belongs to the task asset directory.
- **Resume the source Session from the plugin's own context.** Rejected: Cordis traces a service call to the caller's fiber, so the resumed Agent would be owned by the plugin and cancelled on plugin unload. Use the embedding's activation provider instead.
- **Apply the task's permission/agent preset to the source Session.** Rejected: that silently changes the user's live session and configures it for the plugin's run. Fail closed instead.
- **Refuse to run while the source Session is busy.** Rejected after user choice: dsh's inbox queue already serializes followups, and skipping would make a monitor miss its period silently. The queue is documented as the behavior.
- **Keep an ordinary seeded task and refresh its seed after each run.** Rejected: seed capture is creation-time, and rewriting a user's task asset from a triggered run would race with saves and edits.

## Consequences

- A continuation monitor sees the source session's current persisted context (subject to normal session compaction and retention), including new issues/PRs discovered there, with no seed-size failure and no run-directory copy. The cost is that monitor turns appear inside the user's conversation and share its workspace, model route, and permissions.
- Trigger firing while the source Session runs a turn queues the monitor message; multiple firings queue in order and are subject to the trigger's debounce/rate limits.
- A deleted source Session, an archived or subagent-owned source Session, a missing activation provider, a subagent Agent returned by a provider, or an unreadable registry before publication fails the trigger with a classified dispatch error instead of running a partial task. A handle supplied by a resolver is disposed on those pre-publication failures.
- The plugin never resumes a source Session under its own fiber: Cordis traces service calls to the caller context, so a plugin-owned resume would be cancelled when MaintainAll unloads. Delegating activation to dsh providers keeps the user's source Agent under host/SDK ownership.
- The plugin depends on the embedding's reminder activation path as a compatibility bridge: `schedule/resolve-agent` plus a `sessionController` fallback in the Web profile, or an SDK handler, with `workspaceRegistry` optional for archive checks. This is a reminder-domain mechanism rather than a documented general session-activation API, so the [proposed upstream extension](../../../proposed/architecture/2026-11-03-dsh-session-activation-extension.md) tracks the neutral replacement; until then the bridge is composition-specific, a deployment without an activation provider fails closed, and the plugin never resumes a source Session itself.
- Export/import semantics are explicit: a shared task never carries a continuation target; it imports as a seeded/fresh task on the target machine.
