# Establish a Feedback Path

Use this after identifying enough of the user's intent to choose the next creative decision, and before substantial construction. Prepare the smallest working path from editable material to an inspectable result and a version-linked response. A working existing setup can satisfy this step immediately.

## Choose the path progressively

1. Identify what the user needs to judge next: composition, motion, sound, spatial relationships, interaction, or another concrete property. Choose an image, playback, interactive view, or native application that exposes it.
2. Choose the authoring method and runtime around the intended medium and required features. Read the corresponding row below, then only the selected backend's setup instructions.
3. Reuse available applications and viewers, and complete the setup needed for the selected route.
4. Produce and display the smallest useful result through the intended path. Exercise the required interaction or playback. For reference analysis, inspecting and annotating the supplied material can satisfy this step.
5. Provide the relevant version, a short action to try, and a way to answer. Conversation, an existing viewer, or native controls can collect the response. Carry this path into the next experiment.

| Current need | Read | Verify |
|---|---|---|
| Reference inspection, annotation, static composition or layout | [Visual methods](visual-methods.md) | The actual material or rendered alternative is visible at a useful scale |
| Comparing visual directions and preserving a selection | [Visual variants](../methods/visual-variants/SKILL.md) | Candidate identities, comparison conditions, and the response channel are clear |
| Editable geometry, materials, cloth or avatar behavior | [Tool capabilities](tool-capabilities.md) | The selected application produces the needed view, pose or runtime behavior |
| Movement, sound, sequence or temporal relationships | [Construction methods](iterative-creation.md#detailed-description-and-construction-methods) | The relevant segment can be played and repeated with the required timing and audio |
| Game controls, rules and play experience | [Game engine](../methods/game-engine/SKILL.md) | The native project runs and the chosen local, exported or streamed route supports actual play |

Keep authoring and viewing choices distinct. A browser can display an image, play a recording, execute a Web build, or receive a native application's stream. Select the delivery path that preserves the properties being judged.

## Keep the setup reusable

Keep a compact project-local record of the application/version, source, launch or render command, preview location, tested conditions, and question/answer channel. Identify which preview or build an answer refers to. Record server-side checks and user-device access separately when they have been verified in different places.

Reuse the working path across rounds. Extend it when the next question needs a new capability, such as sound, a different viewpoint, physics, or target-runtime behavior. Follow [Tool capabilities](tool-capabilities.md) for application setup and the [method contract](method-contract.md) for handoff.

Continue with [Intent and evidence](intent-and-evidence.md) to decompose the next decision, then [Iterative creation](iterative-creation.md) to compare alternatives, collect short responses, retain accepted choices, and deepen the result. Setup supplies the means of feedback; the creative loop determines what to test and how the work evolves.
