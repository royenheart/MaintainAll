# Resume Writing

Make the candidate's fit easy to see through selected, credible evidence. Work at two levels: the whole resume establishes a coherent case for the target role; each bullet supplies a distinct contribution. Use the requested resume language and regional conventions, preserving technical names where appropriate. Without an explicit language choice, preserve an existing resume's language; for new content, infer from the target context and conversation.

## Read first, then ask selectively

Read the supplied resume, work notes, job description, and constraints before asking questions. A work summary is sufficient input; an existing resume is optional. Use supplied paths and relevant authorized materials rather than searching unrelated personal files. Preserve the requested scope: a bullet edit does not require redesigning the whole document.

Identify the target role and seniority, audience or application channel, language, and requested deliverable from context. Ask about a missing item when it would change selection or presentation. A full job description helps tailoring but is not a prerequisite for general improvement. When a missing target would change content selection, ask for the intended direction while improving supported content that does not depend on that answer.

For promising experience, distinguish the problem or user need, personal contribution, mechanism or method, relevant tools, delivered outcome, and available evidence. Keep this as working context; do not require a separate profile file or questionnaire.

Use targeted follow-ups when missing information would materially change a claim:

- **Ownership:** establish what the candidate personally designed, implemented, coordinated, or supported before using leadership verbs or attributing team results.
- **Outcome:** ask what changed for users, operations, or the business when notes describe only activity. A delivered capability, adoption, acceptance, or removed manual step can be meaningful without a percentage.
- **Measurement:** ask for a baseline, resulting value, scope, and measurement context when a prominent performance or business claim depends on them. Ask which records or observations support the claim, rather than suggesting an impressive number.
- **Conflicts:** resolve incompatible dates, ambiguous credentials, or contradictory results before asserting the disputed fact.

Start with the few questions that have the highest value, usually one to three closely related questions. Refer to the exact experience and explain briefly which wording the answer would enable. Do not ask again for supplied facts or request every possible metric. Consult [interviewing and evidence examples](references/interviewing-and-evidence.md) when choosing questions or handling incomplete results.

Continue independent edits while waiting. If a claim needs an answer, hold that claim rather than filling it in. When information remains unavailable, use a supported qualitative statement or omit the unsupported part. If there is no factual basis for useful content, ask for the relevant experience instead of inventing a draft. Once the user says a metric is unavailable, move on using other evidence.

## Select the story before polishing lines

Use the target requirements to choose evidence, not to supply candidate facts. Prioritize relevant accomplishments with clear ownership, credible outcomes, and useful scope. Put the strongest role-relevant evidence near the beginning. Preserve accurate titles, employers, dates, credentials, and meaningful career chronology.

Use standard sections appropriate to the candidate: contact information, experience, projects, skills, and education; add other sections only when they contribute. Order sections by relevance and entries within dated sections in reverse chronology. Education can lead for a student; relevant experience usually leads for an experienced candidate. An optional short summary should connect supported strengths to the target role and earn the space it occupies.

For technical projects, use a project name plus a one-sentence overview of its purpose, audience or scope, and a few defining technologies. Put additional relevant tools in contextual bullets or a compact skills section. A technology list alone does not explain the project. Where projects sit under employment, avoid repeating the same achievements in a second projects section.

For a substantial featured project, roughly four to six distinct bullets can work when the evidence and page budget support them. Give secondary projects less space; never pad to a quota. Select complementary contributions such as a central design decision, delivery, performance, reliability, user impact, or collaboration. Each bullet should add evidence rather than paraphrase the overview or another bullet.

Consolidate repetition and reduce irrelevant detail when improving a full resume. Preserve the source material and user-required content; if a shorter application version omits a substantial experience, briefly identify that selection outside the resume. Respect requests to preserve all content or change wording only.

## Write accomplishments at the right depth

Use XYZ as a check for **outcome, measurement, and method**: accomplished X, measured by Y, through Z. Use STAR to recover situation, task, action, and result from raw material. Compress the relevant context into the overview or bullet; do not write four labeled mini-stories for each accomplishment. These frameworks guide evidence selection, not a mandatory sentence order.

Start bullets with a precise action verb that matches the actual contribution. Prefer verbs such as designed, built, automated, migrated, diagnosed, coordinated, or validated over generic responsibility statements. Supporting and collaborative contributions are valid; do not upgrade them to leadership for a stronger verb.

Use either shape when supported:

- **Method first:** action + mechanism or approach + relevant technology + observable outcome.
- **Result first:** improved or delivered outcome + meaningful measure or scope + mechanism that explains it.

Keep one central accomplishment per bullet, normally readable in one or two rendered lines. Put the strongest outcome early enough to scan. Preserve natural wording in the resume's language; avoid repeating a formula merely for consistency.

Explain **what mechanism was designed and what problem it addressed**. Include enough specificity to distinguish the work, such as idempotent event processing, batched database writes, or staged rollout with rollback checks. Stop before internal function names, configuration inventories, call sequences, and implementation walkthroughs. Include a deeper technical detail only when it is itself important evidence for the target role. For nontechnical work, apply the same rule to a process, decision, or intervention and its effect.

Remove unsupported adjectives and labels such as world-class, highly scalable, expert, and excellent communicator. Replace them with the actual contribution or evidence. Preserve useful technical vocabulary; do not reduce every mechanism to a generic business slogan. A skills section should contain relevant, supported capabilities, without proficiency bars or an exhaustive stack inventory. Use the job posting's terminology where equivalent and truthful; new keywords never establish experience.

## Ground results in evidence

Never manufacture metrics, scope, technologies, adoption, titles, or causality. Treat user-provided facts as the starting material, checking ambiguity or inconsistency where it matters. Code can establish a mechanism or implemented feature; it does not establish production traffic, business impact, deployment, or the candidate's personal ownership by itself. Separate delivered results from targets and ongoing work.

Prefer measures relevant to the accomplishment: throughput, latency, accuracy or quality, cost, coverage, reliability, adoption, revenue, or time saved. Scope measures show size, not necessarily improvement. Use the strongest relevant evidence available; not every bullet needs a number.

For numerical claims, retain enough context to avoid changing their meaning: unit, baseline or comparison, population or workload, time window, and test versus production conditions where material. Verify derived arithmetic. Distinguish percentage change from percentage points and latency reduction from a throughput increase. An approximate value or range is usable when the user can explain its basis; retain its approximate status. Do not turn estimates into precise observations or annualize savings from an unstated workload.

Attribute team outcomes alongside the candidate's own contribution. Avoid claiming a technical change caused revenue, accuracy, or reliability gains unless the material supports that connection. When impact is not measured, state a concrete delivered capability or observed change without implying an unmeasured gain.

Keep uncertainty and questions outside copy-ready resume text. Do not add defensive asides, hypothetical caveats, repeated assurances of honesty, or labels such as "if true" inside the resume. Necessary context belongs in direct factual wording, such as "in load tests," "course project," or "contributed to." In a requested working template, explicit placeholders are acceptable; in an application draft, omit unresolved claims and list the remaining questions separately.

## Set the layout and deliver the requested artifact

For ordinary applications, default to a restrained single-column layout, clear headings, text-based contact details, consistent dates, readable type, and selective emphasis. Put essential information in the document body. Use the employer's requested file format. Read [layout and delivery](references/layout-and-delivery.md) for page budgets, visual choices, export, and parsing checks; use it whenever producing or changing document layout.

For a content-only request, provide the revised text in an editable form without forcing an export workflow. For a requested document, preserve the user's format and use available document tools; render and inspect the actual artifact when possible. Review both visual reading and extracted text order. Text extraction is a useful check, not proof of compatibility with every applicant tracking system (ATS). Do not claim universal ATS scores, pass rates, or interview gains.

Match the response to the task: critique when asked to critique, rewritten bullets for a bullet request, or a full resume for a full rewrite. Put the useful result first; add only consequential changes and unresolved questions. During an information-gathering round, a supported partial draft and focused questions are sufficient. Do not attach a mandatory scoring report, cover letter, or interview guide to every task.

Before delivery, check:

- The resume makes the intended role and strongest relevant evidence easy to identify.
- Each featured experience explains purpose and personal contribution; its bullets add distinct evidence at an appropriate technical depth.
- Numbers retain their meaning, credentials and dates agree, and claims can be traced to supplied facts or confirmed answers.
- Wording is direct and specific; repetition, stack dumping, implementation narration, and defensive commentary are removed.
- The requested artifact has consistent formatting; any export or parsing checks claimed were actually performed.

The [research review](references/research.md) records source comparisons, limitations, and the rationale for these rules. Read it when examining or revising the guidance; it is not required for routine resume edits.
